Citibank · EDS Migration Pilot Proposal

Banking ELP + Pega Personalization Pilot

A proposal to validate migrating hosted External Landing Pages (ELP) and Pega-driven personalization into Edge Delivery Services (EDS). Three candidate pages anchor the evaluation — a complex hosted ELP, a post-login Pega banner surface, and a headless credit-cards marketing page — chosen to stress-test session handling, personalization, authoring governance, content release workflows, and dynamic/real-time data integration together.

Project overview

This is a pilot proposal to validate whether Citibank's hosted pages and Pega-driven personalization surfaces can migrate cleanly to Edge Delivery Services, without losing session-aware personalization, authoring governance, or release control. Scenario 3 (Credit Cards Explore) now has an initial EDS build — its page structure has been re-modeled as blocks and rendered in preview; the personalization, session, and engagement-module items remain open. Scenarios 1 and 2 are not built yet. This document scopes what each one is meant to prove and what still needs an answer before pilot kickoff.

Purpose

  • Validate a hosted-page migration path from the existing banking.citi.com ELP platform into EDS.
  • Validate the authoring workflow and governance model changes EDS requires for hosted pages.
  • Validate dynamic, real-time data rendering — Pega decisioning and AEM GraphQL-backed personalization — inside an authored EDS page.
  • Validate headless-to-block migration for an existing Angular experience, including session-aware header/footer branding.
  • Validate an authoring & release workflow that supports bi-weekly content releases without colliding with monthly engineering releases.

Scenario 1 — Citigold Featured Offer (ELP) Proposed

Live (production, migration source): banking.citi.com/cbol/om/checking/citigold/featured-offer/default.htm

This is one of our most complex hosted External Landing Pages (ELP) and a strong fit for the prototype because it exercises three things at once: whether a hosted page can transition into EDS, how the authoring and governance model needs to evolve for hosted pages, and whether EDS can render dynamic API data reliably inside an authored page.

What this validates

  • Hosted page migration path — demonstrates how a hosted page could transition into EDS as part of the broader cloud migration strategy.
  • Authoring workflow changes — surfaces how the authoring experience and governance model need to evolve for hosted pages moving to EDS.
  • Dynamic API integration — the page consumes dynamic API data; validates how EDS handles real-time data rendering inside an authored page structure.
  • Render the hosted ELP structure through EDS
    Reproduce the Citigold Featured Offer layout, content model, and section structure as authorable EDS blocks.
  • Fetch and render dynamic API data
    Confirm the offer/eligibility data that currently comes from the hosted page's backend can be fetched and rendered client-side (or edge-side) from an EDS page.
  • Preserve session handling
    Confirm any session state the hosted page relies on carries across into the EDS-rendered page without breaking eligibility/offer logic.
  • Define the authoring & governance model
    Decide who authors this page, what approvals are required, and how content release maps onto the existing hosted-page release process.

Pega banner E2E gate — publish blocker

This page carries a hard release requirement: it must be validated end-to-end with Pega banner testing before it is ever published live.

Release gate. The EDS preview page must have its Apply Now click-through pointed at Citi UAT for Pega banner testing, and that end-to-end path must be verified before the page is published to live. Publish should be blocked until this test passes.
  1. Point preview's Apply Now to Citi UAT

    Configure the EDS preview environment so the Apply Now CTA on the Pega banner routes to the Citi UAT environment, not production.

  2. Run the Pega banner E2E test on preview

    Validate the banner renders correctly, the decisioning call resolves, and the Apply Now click-through completes against Citi UAT.

  3. Re-point to production before publish

    Once the UAT-backed E2E test passes, switch the Apply Now target to production and only then promote the page to live.

Open questions

1. How is the preview → UAT / live → production banner-target switch mechanized? Is this an environment variable, a page-level config, or a manual step before promotion — and how do we prevent a page from accidentally publishing with the UAT target still wired in?
2. What exactly is the dynamic API data on this page, and where does it come from? The requirements only say the page "consumes dynamic API data" without naming the API, its payload, or its source (offer eligibility, pricing, terms?). Confirm the source, its auth model, and whether it can be called from an EDS-rendered page without a server-side proxy. Flagged again during the initial engineering review as still unclear.
3. Who owns approval for the authoring/governance model change? Hosted pages today likely have a different review chain than EDS-authored pages — this needs sign-off before the pilot can be considered representative of the real migration.
4. The Citi brief describes this scenario relative to two related pages, but only one URL was provided (.../featured-offer/default.htm). Confirm what the second page is and get its URL before scoping the ELP structure further — it may change the content model.

Scenario 2 — Personalized Post-Login Banners Proposed

A third use case: post-login personalized banners powered by Pega and rendered dynamically across specific placements on post-login pages. Because these are post-login experiences, there is no shareable page URL — the content is fetched from the AEM personalization endpoint below.

What this validates

  • Post-login context — banners render only after customer authentication, so EDS must integrate with session and identity state.
  • Pega integration — content is driven in real time by the Pega decisioning engine based on customer profile and segment data.
  • Placement flexibility — banners appear across multiple placements on post-login pages, so EDS needs to support dynamic, slot-based rendering.

Content release & the branch model

The original brief asked for: sync production content to lower environments immediately post-release; if conflicts exist there, generate a conflict report and halt the merge rather than auto-resolving; and monthly tech releases must never override the regular content releases.

This isn't actually an EDS problem. That requirement describes a topology with separate author/stage/dev instances, each holding its own copy of content that can drift out of sync with production — which is how AEM Managed Services works, but not how EDS works. In EDS there is exactly one content source (the authoring tool — Document Authoring or AEM), and every environment renders that same source through the Admin API: Preview always reflects the current authored state, Live always reflects the last-published state, and every git branch gets its own preview of that same content. There's no separate "lower environment" copy of content to sync into or drift out of sync with, so there's nothing to conflict-check or halt on.

How branches replace lower environments

The isolation "lower environments" used to provide for engineering work comes from git branches instead of separate deployed instances:

  • Every branch gets a live preview automatically at {branch}--{repo}--{owner}.aem.page — no provisioning, no deploy step, no separate environment to keep in sync.
  • That branch preview renders the same authored content as production, through whatever code is on that branch — an engineer testing a monthly tech change sees real, current content rendered against their in-progress code, not a stale or duplicated copy.
  • Promoting a tech change is a normal PR merge to main, which only touches code. It can't overwrite a content release because content documents live in the authoring tool, not in the code repo or the merge.
  • Publishing a content change (bi-weekly or otherwise) is a Preview/Publish action in the authoring tool, independent of whatever engineering branches happen to be open at the time.

Residual question for Citi. Worth confirming they don't mean a different, real concern that DA/AEM already solves separately — e.g. two authors editing the same document at the same time. That's a content-locking/versioning question the authoring tool handles on its own, and it's a genuinely different problem from the prod→lower-env sync described in the brief.

Open questions

2. Where/how is the credit card product data stored, and what serves it to the page today — the same GraphQL layer used for the banner and nav, a separate product-catalog API, or something else?
3. How do sessions and personalization work for an unauthenticated visitor? This page doesn't require login, so it isn't obvious what identity signal drives the segment-driven banners/pricing for an anonymous user — a device cookie, IP/geo, a prior-visit signal, something else?
